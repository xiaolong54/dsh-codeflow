# 设计：给 agent 用的地图

codeflow 只有一个读者：写代码、改 bug 的那个模型。它没有界面——没有侧边栏页签，没有画布，没有自己的对话区。它只有两样东西：

1. **一个工具** `codeflow_map`：把项目读成「用数据流连起来的功能块」。
2. **一段提示词**：告诉模型代码该写成什么样，以及出问题时该怎么顺着数据去找。

## 为什么是这两样

用户要的是「agent 写好代码、agent 能改错」。这两件事靠的都是同一件事：**知道数据从哪来、到哪去**。

- 写好代码 → 下一个功能要能被单独读懂、单独替换。模型得先看见现有的块长什么样，才知道该照着什么写。
- 改错 → 症状出现在的地方通常不是问题所在的地方。模型得能顺着值回到生产它的那个块。

所以地图必须是**结构**的（谁调用谁），而不是文本的（grep 一段代码）；必须是**带值**的（这条边搬的是哪个值），而不只是调用关系。

## 一份模型，在宿主那边

宿主扫描项目、解析出功能块、块之间的调用、跟着调用走的值、结构问题。模型只有一份：工具的每个回答都来自同一次扫描（`src/host/analyze.js`），短时间内重复问不会重复扫。

工具只回答问题，不动手：`src/host/tool.js` 里没有一行写文件。改不改、怎么改，是模型的决定。

## 提示词怎么写

提示词分三段，顺序是有意的（`src/host/tool.js` 的 `PROMPT`）：

1. **地图是什么**：代码是功能块，块之间的边是调用和值；`codeflow_map` 读的就是你正要改的这份代码。
2. **两件活**：
   - 写模块化、可组装的代码——六条规则（一个功能一个具名函数、入口只编排、数据进参数出返回值、每个函数一行说明、块要小、跨文件只用静态 import）。
   - 改 bug 靠顺着数据，不靠猜症状——从出症状的块出发，沿值往回走到生产它的块，改生产者或边界，而不是改症状出现的地方。
3. **每个动作什么时候用**：`file` 是改某个文件前先读它；`flow` 是查一个块收什么值、传什么值；`block` 是看一个块的全貌；`area`/`overview`/`contracts`/`scaffold`/`convention` 是更大的视角。

规则不只是提示：它们同时是**机器可查的项**，模型能查自己有没有守住（`action=diagnostics`）。

| 项 | 判据 | 严重性 |
| --- | --- | --- |
| `missing-doc` | 函数/方法上方没有一行说明 | 提示 |
| `orchestrator-entry` | 入口块超过 12 行，却调不到两个具名块 | 提示 |
| `inline-callback` | 匿名回调体超过 10 行且有 return | 提示 |
| `nested-definition` | 块里又定义了具名函数 | 提示 |
| `block-too-large` | 超过 80 行 | 警告 |
| `too-many-params` | 超过 6 个参数 | 警告 |
| `module-mutable-state` | 模块级可变状态 | 警告 |
| `hidden-data-flow` | 直接改写不是参数的变量 | 警告 |
| `explicit-io` | 直接写不是参数的变量 | 警告 |
| `ambiguous-call` | 一个名字在多个文件里都有定义 | 警告 |
| `dynamic-dispatch` | 反射/动态 import 让调用目标无法静态确定 | 警告 |

每条问题都带 `kind`：`flow`（数据流坏了）或 `convention`（不够模块化）。

## 工具的九个动作

| 动作 | 回答什么 |
| --- | --- |
| `file` path=文件 | 这个文件有哪些块、块之间怎么调、每次调用搬什么值，以及源码 |
| `block` path=文件 name=块 | 一个块的全部：入参、返回值、谁调用它、它调用谁、源码 |
| `flow` path=文件 name=块 | 只看这个块收进来的值和传出去的值——查 bug 时用得最多 |
| `area` path=分区 | 一个功能分区的所有块和数据流 |
| `overview` | 项目的分区、入口点、问题清单 |
| `contracts` | 对外的块，以及谁依赖它们 |
| `diagnostics` | 数据流已经断了的地方 |
| `scaffold` path=范围 | 这个范围该怎么搭（模块蓝图） |
| `convention` | 项目守住了多少模块化规则 |

每个回答有两种形态：`text` 是模型读的，`facts` 是同一份事实的数据形态。

## 不做的事

- **没有界面**：不注册侧边栏页签，不画图，不开自己的对话区。用户看到的就是 agent 写出来的代码。
- **不写文件**：插件只读；改动由模型的其它工具做。
- **不替人决定模块怎么分**：它给「现状 + 规则 + 蓝图」，分法由模型和用户确认。
- **不做第二份模型**：模型只有宿主那一份。

## 参考

- [Aider 的 repo map](https://aider.chat/docs/repomap.html)：模型每次请求都拿到一份仓库的简图——关键符号和调用签名。
- [Zed 的 agent panel](https://zed.dev/docs/ai/agent-panel)：上下文是显式附上的而不是靠猜的。本插件不做面板，但同样把上下文显式交给模型。
